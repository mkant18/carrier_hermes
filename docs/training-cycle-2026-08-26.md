## Self-Training Method Recommendations (Part A findings)

Current external research on agent-fleet self-improvement converges on a **layered adaptation stack**, cheapest-first (Zylos 2026): (0) context-time injection of learned rules/preferences, (1) memory/skill consolidation (no gradient updates), (2) preference-pair fine-tuning (DPO) on divergence points between success/failure trajectories, (3) full weight updates — rarely justified below fleet scale. APEX (arXiv 2606.15363) shows a 15-node fleet extracting reusable behavioural principles from ~114 real task traces via a local qwen2.5-coder:32b, at ~$0 marginal cost — directly analogous to carrier_hermes's Ollama setup.

**Recommendation for carrier_hermes, in priority order:**

1. **Layer 0 (immediate, zero-cost): Correction replay → SOUL.md/skill patches.** The fleet already has 48h of concrete failure→fix pairs (below). The highest-ROI "training" isn't model weights, it's converting each recurring failure into a rule injected at context time (SOUL.md sections, skill patches, task-template defaults). This is what APEX calls "principle extraction" and it requires zero GPU/OAuth spend.
2. **Layer 1 (near-term): Memory/skill consolidation via local LLM.** Use Ollama to batch-summarize Kanban task histories weekly into "lessons" (structured JSON: trigger → failure mode → correction), stored as skill/memory entries. This is mechanical extraction, not RLHF — safe, cheap, no billing-guard risk.
3. **Layer 2 (Phase B candidate): Divergence-point preference pairs for routing/dispatch decisions.** carrier_hermes has strong success/failure trajectory pairs already (e.g., Wrench dispatching fabricated-vs-verified Mate sorties). ToolGraph+DPO (arXiv 2606.23112) shows real gains from exactly this shape of data: locate the turn where success and failure trajectories diverge, label chosen/rejected, and DPO-tune the **local Ollama model only** (never the OAuth-routed frontier models — no billing/ToS surface). This is the natural Phase B target once enough labeled pairs exist (~50-100 minimum).
4. **Not recommended now:** RLHF-style reward-model training or full fine-tuning — too heavy for current data volume (~30 tasks/48h) and infrastructure; the local-only DPO path captures most of the benefit at a fraction of the engineering cost.

**Data sources available in-fleet:** Kanban task history (events, comments, run metadata — richest source), `result`/`metadata` fields on completed tasks, session logs (session_search), and board.json config. No dedicated failure-log or session_model_usage table was found exposed to this agent — Part B below was built entirely from Kanban task/event/comment data, which is sufficient for Layer 0/1 but would need structuring (e.g., a `lessons.jsonl`) before Layer 2 DPO pair construction.

## Recommended Memory/Skill Updates (top 3 actionable changes)

1. **Task-creation checklist/skill for orchestrator profiles (Helm/Wrench):** before calling `kanban_create` with `workspace_kind='worktree'`, always pass an explicit `workspace_path`; never rely on board defaults being set. This directly targets the largest failure class (26+ retries) and is a one-line habit change, not a code fix.
2. **Escalation-after-N-failures rule:** if the same assignee profile fails/blocks/fabricates on a task 2 times, the next dispatch must go to a *different* execution path (a different profile, or direct execution by the orchestrator) rather than a 3rd identical retry. This would have saved ~6 of the 11 cycles on t_e9dd9dbc and both t_9d2f045e retries.
3. **SOUL.md/agent-instruction-file edits are human-gate-only, permanently.** Do not create skills or task templates that attempt automated SOUL.md edits, and do not sanction terminal-level bypasses (`sed`) of the write-protection guard — that workaround used on t_e9dd9dbc should be treated as an incident, not a pattern. Add this explicitly to the task-creation skill so future auto-decomposer output routes SOUL.md changes straight to `kanban_block(kind='needs_input')` instead of spawning Mate sorties against it.
